# Call Me Maybe — Introduction to Function Calling in LLMs

## Description

This project implements a function calling system that translates natural language
prompts into structured function calls using a small Large Language Model (LLM).

Given a prompt like:
```
"What is the sum of 40 and 2?"
```

The system produces:
```json
{
  "prompt": "What is the sum of 40 and 2?",
  "name": "fn_add_numbers",
  "parameters": {"a": 40.0, "b": 2.0}
}
```

The core challenge is achieving 100% valid JSON output using **constrained decoding**
— a technique that guides the model token-by-token to guarantee valid structure,
without relying on prompting alone.

## Algorithm Explanation

### Constrained Decoding

The core of this project is **constrained decoding** — a technique that intervenes
in the token generation process at each step.

A language model generates text one token at a time:
1. The model produces logits (probability scores) for all possible next tokens
2. Normally you pick the highest scoring token
3. With constrained decoding, before picking, you set all invalid tokens to `-inf`
4. This forces the model to only generate valid tokens

### Generation Pipeline

```
Prompt → Tokenization → Input IDs → LLM → Logits → Mask Invalid → Pick Best Token
                                                                          ↓
                                                              Append to sequence
                                                                          ↓
                                                              Repeat until done
```

### Prefix Matching

For function name generation, we use prefix matching:

1. Start with empty prefix `""`
2. At each step, find all valid function names that start with current prefix
3. Find all vocabulary tokens that, when appended, still match at least one valid name
4. Only allow those tokens
5. Stop when prefix exactly matches a complete function name

Example:
```
prefix=""         → allows tokens: "fn", "f", etc.
prefix="fn"       → allows tokens: "_add", "_greet", "_reverse", "_"
prefix="fn_"      → allows tokens: "add", "greet", "reverse"
prefix="fn_greet" → exact match → stop
```

### Schema Enforcement

The output JSON must follow an exact schema:
```json
{"name": "<function_name>", "parameters": {"<arg>": <value>}}
```

Structural tokens like `{`, `"`, `:`, `,`, `}` are **forced directly** — the model
never chooses them. Only the function name and argument values are generated by the
model, both under strict constraints.

---

## Design Decisions

### Why Force Structural Tokens?

Instead of letting the model generate `{`, `"`, `:` etc., we force them directly
using their known token IDs. This guarantees the JSON structure is always correct
regardless of what the model would naturally generate.

### Why Pydantic For Validation?

Pydantic provides automatic type validation and clear error messages. Any malformed
input file is caught immediately with a descriptive error rather than a cryptic crash.

### Why Separate `constraints.py`?

The constrained decoding logic is kept separate from the generation loop. This makes
it testable in isolation and reusable for different generation scenarios.

### Token Constants

Hardcoded token IDs are defined as named constants at the top of `generator.py`:
```python
TOKEN_OPEN_BRACE = 90
TOKEN_QUOTE = 1
TOKEN_COLON = 25
```
This makes the code readable and easy to update if the model changes.

## Performance Analysis

### Accuracy

- **Function selection**: 100% on standard prompts
- **Number extraction**: 100% on positive numbers, limited on negative numbers
- **String extraction**: 100% on standard strings
- **Overall**: 90%+ on the provided test suite

### Speed

Each prompt requires one forward pass per token generated. On CPU:
- Simple prompts (1-2 parameters): ~10-30 seconds
- Complex prompts (3+ parameters): ~30-60 seconds

The Qwen3-0.6B model has 600M parameters requiring ~2.4GB memory.

### Reliability

- **JSON validity**: 100% — constrained decoding guarantees valid JSON every time
- **Schema compliance**: 100% — parameter types always match function definitions
- **Error handling**: All edge cases return graceful error messages

## Challenges Faced

### 1. Tokenizer Space Encoding

The tokenizer uses `Ġ` to represent spaces inside tokens. `"hello world"` becomes
`["hello", "Ġworld"]`. This required careful handling in:
- String value generation (replacing `Ġ` with real spaces)
- Number token filtering (stripping `Ġ` before checking if token is numeric)

### 2. Token Context Dependency

Encoding a string in isolation produces different token IDs than encoding it in
context. For example `model.encode('{"name": "')` gives different IDs than the
same string embedded in a longer sequence. This meant all structural tokens had
to be forced using their known vocabulary IDs, not re-encoded.

### 3. Infinite Loop Prevention

Early versions of the generation loops had infinite loop bugs because:
- Stop tokens were masked out (so they could never be picked to break the loop)
- The model kept picking the same token repeatedly

Fixed by including stop tokens in the valid set and breaking when they are picked.

### 4. Negative Numbers

Small models struggle with argument ordering when negative numbers are present.
The model associates positive numbers with parameters first. Partially addressed
using regex extraction from the original prompt when negative numbers are detected.

## Testing Strategy

Tests are organized in the `tests/` directory by module:

- `test_constraints.py` — vocabulary loading, logit masking, prefix matching
- `test_loader.py` — file loading, JSON validation, error handling
- `test_schema.py` — Pydantic model validation, field validators
- `test_generator.py` — prompt building, input validation

Run all tests:
```bash
uv run pytest tests/ -v
```

Edge cases tested:
- Missing input files
- Invalid JSON files
- Invalid function name formats
- Empty prompts
- Short prompts
- No matching function found

## Example Usage

```bash

```

### Custom Input/Output

```bash
uv run python -m src \
  --functions_definition my_functions.json \
  --input my_prompts.json \

```

### Input Format

`functions_definition.json`:
```json
[
  {
    "name": "fn_add_numbers",
    "description": "Add two numbers together and return their sum.",
    "parameters": {
      "a": {"type": "number"},
      "b": {"type": "number"}
    },
    "returns": {"type": "number"}
  }
]
```

`function_calling_tests.json`:
```json
[
  {"prompt": "What is the sum of 3 and 7?"},
  {"prompt": "Greet john"}
]
```

### Output Format

`function_calls.json`:
```json
[
  {
    "prompt": "What is the sum of 3 and 7?",
    "name": "fn_add_numbers",
    "parameters": {"a": 3.0, "b": 7.0}
  },
  {
    "prompt": "Greet john",
    "name": "fn_greet",
    "parameters": {"name": "john"}
  }
]
```
